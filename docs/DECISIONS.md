D18 (2026-10-23 explicit owner answer): Ordinary settings are exactly six concepts: user entry port, destination host, destination port, transport connection port, transport kind with a plain-language explanation, and shared token. D21 — PROPOSAL ONLY, owner decision pending (VLESS): use an owner-supplied dedicated synthetic test identity, never a paying user's account. A URI can be used transiently for a manual check; persistent scheduled checks would need separately approved encrypted storage of that synthetic identity. A pinned xray or sing-box binary would run in a short-lived constrained non-root process on the destination probe origin, with explicit allowed entry/egress targets, one concurrent probe, small response limit, strict timeout and isolated temporary files. It would test an allowed HTTPS canary through the actual user entry and report origin/target/time/protocol separately from TCP/TLS. Benefits: protocol-level evidence. Costs: an extra versioned binary/security update surface, canary dependency, credential lifecycle and resource use that must be measured in the lab. A timeout cannot by itself distinguish subscription, censorship, DNS, routing or remote application failure. Reject arbitrary URLs/egress and never run a user-provided shell command. No core is downloaded, run or added to the architecture before approval. Existing HTTP/TCP/TLS checks remain explicitly not proof of VLESS.

D22 — PROPOSAL ONLY, owner decision pending (optional SSH bootstrap): keep the current outbound native-agent architecture. An optional one-time SSH installation could accept a password only in memory, verify the full host fingerprint before authentication, preview the fixed bootstrap/version/checksum and owned paths, and discard credentials on success/failure. It would not save passwords, offer arbitrary shell text or modify SSH policy. Elevated bootstrap would require the minimum setup authority already described by the installer. Benefits: less terminal work; costs: handling credentials in the controller, an additional SSH/privilege path and recovery UX. The ordinary copy-command/enrollment flow remains supported. No SSH client, credential persistence or automatic host trust is implemented by this proposal.

D23 — PROPOSAL ONLY, owner decision pending (agent privilege): the current agent is a root service with the existing systemd hardening and typed/path/ownership checks. It is not described as unprivileged. Retaining it avoids a new service and supports owned/adopted systemd operations, but compromise still has a broad authority boundary. A lower-privilege design would split observation and mutation into an unprivileged agent plus a narrowly scoped local privileged helper, with fixed operation schemas, protected manifest/revision checks and peer rollback timers. This adds an IPC boundary, packaging/upgrade complexity and compatibility work for existing root-owned configurations and adopted units. Design and test the exact capability/path matrix before any such change; do not silently implement a new root/sudo/SSH model. This correction retains the current architecture while awaiting the owner's answer.

D24 (2026-10-23, implementation detail): keep the approved visual system but make home action-first; collapse logical topology. Resource/history charts use actual aggregation intervals and null/gap semantics. Enrollment polling uses a narrowly scoped authenticated read-only POST so a token never enters URL/access logs. It retains origin and general API/session rate limits; only the separate mutation budget is reserved for real writes. No SSH/root authority change follows. The current CLI-required enrollment command is explicitly incomplete as fresh-host bootstrap; do not advertise installation progress that is not measured.

D25 (fresh-node bootstrap within existing installer): distribute the same running controller program for a matching Linux architecture through the existing HTTPS service, with pinned SHA256, fixed paths, single-download concurrency and bounded file size/rate. This removes the preinstalled-CLI prerequisite without depending on publishing an unrelated release. Binary/script are public open-source program bytes, never private runtime files. TLS is the distribution trust boundary; checksum is integrity, not an independent publisher signature. Tradeoffs: one extra bounded download path and only the controller's built architecture initially; mismatches require the existing separately verified matching artifact flow. Root installation still uses the current explicit native setup preview/confirmation and hardened root agent; no new root/SSH authority or privileged service is introduced. Never auto-download or install on production from the development task.
